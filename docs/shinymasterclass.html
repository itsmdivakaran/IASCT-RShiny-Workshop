Module 01

What is R Shiny?

Shiny is an R package, created by Posit (formerly RStudio), that turns R analysis code into interactive web applications without requiring HTML, CSS, or JavaScript.

Turning an R script into something a non-programmer can click around in a browser normally means learning an entire front-end stack: HTML for structure, CSS for style, JavaScript for interactivity, plus a server language to run statistics. Shiny collapses all of that into one language. You describe what the app should show and how it should react to input, entirely in R, and Shiny generates and manages the web layer underneath.

The mental model: two halves, one conversation

Every Shiny app is built from exactly two pieces that talk to each other continuously while the app is running:

  • UI (user interface) — a description of what the browser should display: buttons, sliders, plots, tables, text. Written declaratively, as nested R function calls that generate HTML.
  • Server — a function containing your actual logic: reading input values, computing results, producing output. It runs on the R process, not in the browser.
Fig. 1 — the browser only displays; every computation happens back on the R process.

When a user drags a slider or clicks a button, the browser sends that value to the R process over a persistent WebSocket connection. R re-runs only the pieces of your server logic that depend on that value, and pushes back just the HTML/JSON needed to update the screen. The page never reloads. This "recompute only what changed" behavior is called reactivity — the idea the entire framework is built around, and the subject of all of Part III.

Why teams reach for Shiny

You already have the analysis in R — a model, a ggplot, a data pipeline. Shiny exposes it as a live tool without rewriting logic in another language.

What Shiny is not

Not a static site generator (that's R Markdown/Quarto), and not stateless like a typical REST API — each session keeps a live R process running for as long as the tab is open.

Where Shiny sits in the R ecosystem

Shiny is one project inside a wider Posit-maintained web stack. Knowing the map helps you find the right tool later:

Module 02

How Shiny works under the hood

Understanding the request lifecycle demystifies almost every confusing error message you'll hit later.

The lifecycle of a session

  1. Initial HTTP request. The browser requests the app's URL. httpuv (Shiny's embedded web server) serves back the initial HTML generated from your ui object.
  2. WebSocket handshake. The page's JavaScript (shipped by Shiny automatically) opens a persistent WebSocket connection back to the R process.
  3. Server function invocation. R calls your server(input, output, session) function once for this connection, creating a new, isolated reactive environment.
  4. Reactive flush cycle. Whenever an input changes, the new value is pushed over the WebSocket. Shiny walks its internal dependency graph, recomputes only the reactive expressions and outputs that depend on that input, and streams the resulting HTML/JSON patches back.
  5. Session end. When the tab closes or the connection drops, Shiny tears down that session's reactive environment and frees its memory.
One R process, many sessions (or one each)

By default, a single Shiny process can serve many simultaneous browser sessions — each gets its own isolated call to server(), so one user's input$ values never leak into another's. Production deployments (Module 42) often run several R processes behind a load balancer for concurrency and fault isolation.

The reactive flush cycle, conceptually

Shiny doesn't recompute your whole app on every change. Internally, it maintains a dependency graph — a record of which reactive expressions read which reactive values. When a value becomes "dirty" (changed), Shiny marks everything downstream of it as invalidated, then re-runs only the invalidated pieces, in dependency order, once per flush. This is why Module 22 (The Reactive Graph) matters so much: it's not an abstraction bolted on top of Shiny, it's the actual execution engine.

💡 Why no page ever "reloads"

Because updates travel as small JSON patches over an already-open WebSocket, a Shiny app can update a single plot 10 times a second without the browser ever navigating — this is what makes drag-a-slider-and-watch-it-update feel instant.

Watching the flush cycle happen, live

You can make the lifecycle above concrete by printing messages from both zones of the server function and watching the R console while you interact with a running app:

server <- function(input, output, session) {
  message("1. Session started")   # prints once, at connection time

  output$echo <- renderText({
    message("2. Flush: recomputing output$echo")   # prints on every input$x change
    input$x
  })
}

Run this, open the app, and change the input a few times — "1. Session started" prints exactly once per browser tab, while "2. Flush: recomputing..." prints once per change, always immediately after the corresponding WebSocket message arrives. For a full graphical version of this trace, see reactlog in Module 38.

By default, saving app.R while the app is running does not restart it automatically in a plain R console — you stop and re-run. RStudio's Viewer, and packages like shiny's own dev mode, can watch the file and reload for you:

Module 05

Anatomy of a Shiny app

Three ingredients, always in the same order: a UI, a server function, and the call that wires them together.

library(shiny)

# 1. UI — describes what the browser shows
ui <- fluidPage(
  titlePanel("Hello, Shiny"),
  sidebarLayout(
    sidebarPanel(
      sliderInput("bins", "Number of bins:", min = 5, max = 50, value = 20)
    ),
    mainPanel(
      plotOutput("histPlot")
    )
  )
)

# 2. Server — describes how the app reacts to input
server <- function(input, output, session) {
  output$histPlot <- renderPlot({
    hist(faithful$waiting,
         breaks = input$bins,
         col = "steelblue", border = "white",
         main = "Old Faithful eruption waiting times")
  })
}

# 3. Run — wire UI and server together and launch
shinyApp(ui = ui, server = server)

Walk through what's happening line by line:

  • fluidPage(...) builds a responsive HTML page. Anything nested inside it becomes part of the page layout (Module 09).
  • sliderInput("bins", ...) creates a control with ID "bins". Inside the server, its current value is always available as input$bins.
  • plotOutput("histPlot") reserves a spot in the UI with ID "histPlot" where a plot will be drawn.
  • server <- function(input, output, session) is called once per browser session. input is read-only, output is write-only, and session gives access to lower-level session info (Module 28).
  • output$histPlot <- renderPlot({ ... }) assigns a reactive recipe — "whenever this block's dependencies change, re-run it and redraw." You never call this yourself.
  • shinyApp(ui, server) creates the app object and, when run, starts the local web server.
⚠ The ID contract

Every input/output pair is connected purely by matching strings: the ID given to sliderInput("bins", ...) must exactly match input$bins. There's no compiler to catch a typo — a mismatched ID silently renders nothing.

A second example: a text transformer

A smaller app makes the same three-piece pattern easier to see without the plotting code competing for attention:

library(shiny)

ui <- fluidPage(
  textInput("phrase", "Enter a phrase"),
  radioButtons("mode", "Transform", choices = c("UPPERCASE", "lowercase", "Title Case")),
  h3(textOutput("result"))
)

server <- function(input, output, session) {
  output$result <- renderText({
    switch(input$mode,
      "UPPERCASE" = toupper(input$phrase),
      "lowercase" = tolower(input$phrase),
      "Title Case" = tools::toTitleCase(input$phrase)
    )
  })
}

shinyApp(ui, server)

Same shape as the histogram app: one input feeding one render*() block. Notice there's no plotOutput/renderPlot anywhere — the UI↔server wiring pattern is identical regardless of what kind of output you're producing.

Module 06

The UI object, explained

The ui object is not "code that runs" in the usual sense — it's a static tree of HTML built once, before any user connects.

A subtle but important point: ui <- fluidPage(...) executes exactly once, when the app starts (or, for the function form below, once per new session). It is not reactive. Any R code inside it — like Sys.time() or sample() — runs a single time and its result is frozen into the HTML sent to every visitor, unless you switch to a function-based UI.

# A UI as a fixed OBJECT — evaluated once, ever
ui <- fluidPage(
  p(paste("Page built at:", Sys.time()))   # frozen at app startup
)

# A UI as a FUNCTION of the request — evaluated once per new session
ui <- function(request) {
  fluidPage(
    p(paste("Session started at:", Sys.time()))  # fresh per visitor
  )
}
💡 When you need the function form

Use ui <- function(request) {...} whenever the UI must depend on something per-request: reading URL query parameters (parseQueryString(request$QUERY_STRING)), bookmarking (Module 28), or per-user theming based on cookies.

The UI is just a nested HTML tree

Every layout and input function you call (fluidPage(), sidebarPanel(), sliderInput()...) is, underneath, building and returning htmltools tag objects. You can inspect this directly:

sliderInput("bins", "Bins", 1, 100, 50)
#> <div class="form-group shiny-input-container">
#>   <label class="control-label" id="bins-label" for="bins">Bins</label>
#>   <input class="js-range-slider" id="bins" data-min="1" data-max="100" ... />
#> </div>

This is why nesting UI functions inside each other (sidebarPanel(sliderInput(...))) works exactly like nesting HTML tags — because that's precisely what's happening.

Module 07

The server function, explained

Unlike the UI, the server function's body re-executes constantly — but understanding exactly what re-runs, and when, is the single most important skill in this guide.

server <- function(input, output, session) {

  # Runs ONCE per session, when a user first connects —
  # good for one-time per-session setup.
  message("New session started")

  # Runs EVERY TIME input$n changes — this is a reactive context.
  output$doubled <- renderText({
    input$n * 2
  })
}

Code written directly in the body of server(), outside any reactive()/observe()/render*() block, runs exactly once per session — when that user's connection is established. Code inside a reactive block re-runs whenever its dependencies change. Confusing these two zones is the single most common source of "why isn't my app updating" bugs for beginners.

Where the code livesHow often it runs
Top level of server(), outside any reactive blockOnce, when the session starts
Inside reactive({})Lazily, only when read and only if stale
Inside observe({}) / render*({})Automatically, whenever a dependency changes
Top level of the R script, outside server() entirelyOnce, when the app starts (shared by all sessions)

Builds directly toward → Module 22 — The Reactive Graph, where we explain precisely why dependency-tracking makes this table true.

Seeing the timing difference directly

server <- function(input, output, session) {

  message("Top-level: runs once, at connection time")
  startup_constant <- Sys.time()          # fixed for the whole session

  output$now <- renderText({
    message("Inside renderText: runs on every input$refresh change")
    paste("Session started:", startup_constant, "| Now:", Sys.time())
  })
}

Pair this with an actionButton("refresh", "Refresh") in the UI and read input$refresh inside renderText() — the "Session started" timestamp never changes across clicks, while "Now" updates every time, making the two execution zones visibly different rather than just theoretically different.

Module 08

Project structure & Express syntax

Three valid ways to arrange the same app — pick based on size and team convention.

Single-file: app.R

The modern default for anything under a few hundred lines. Everything — libraries, UI, server, the shinyApp() call — lives in one file.

Two-file: ui.R + server.R

library(shiny)

fluidPage(
  titlePanel("Hello, Shiny"),
  sidebarLayout(
    sidebarPanel(
      sliderInput("bins", "Number of bins:",
                  min = 5, max = 50, value = 20)
    ),
    mainPanel(
      plotOutput("histPlot")
    )
  )
)
library(shiny)

function(input, output, session) {
  output$histPlot <- renderPlot({
    hist(faithful$waiting,
         breaks = input$bins,
         col = "steelblue",
         border = "white")
  })
}

Shiny detects this pair automatically — no shinyApp() call is needed in either file. Useful when a large team wants UI and server changes to show up as separate diffs in version control.

Express syntax (shiny 1.9+)

A newer, more compact syntax for smaller apps, inspired by Shiny for Python — inputs, outputs, and layout are declared inline without a separate ui object:

library(shiny.express)

sliderInput("bins", "Number of bins:", min = 5, max = 50, value = 20)

renderPlot({
  hist(faithful$waiting, breaks = input$bins, col = "steelblue", border = "white")
})
Which should you use?

This guide uses classic ui/server syntax throughout, since it's what you'll encounter in the vast majority of existing apps, tutorials, and Stack Overflow answers. Express syntax is worth knowing exists, but classic syntax is the shared vocabulary of the Shiny world.

Module 10

The 12-column grid system

For anything more custom than a sidebar, Shiny exposes Bootstrap's 12-column grid directly.

Each fluidRow() is a row; each column(width, ...) inside it claims that many of the 12 available columns. Widths in the same row should sum to 12 or less.

ui <- fluidPage(
  fluidRow(
    column(4, wellPanel("Left third — width 4")),
    column(4, wellPanel("Middle third — width 4")),
    column(4, wellPanel("Right third — width 4"))
  ),
  fluidRow(
    column(8, wellPanel("Two thirds — width 8")),
    column(4, wellPanel("One third — width 4"))
  ),
  fluidRow(
    column(6, offset = 3, wellPanel("Centered half-width column"))
  )
)
💡 Nesting rows inside columns

A column() can itself contain a fluidRow() — this is how you build grids-within-grids, like a dashboard card that internally splits into a chart and a legend.

Responsive widths across screen sizes

Bootstrap's grid supports breakpoint-specific widths, so a column can be full-width on a phone and a third-width on a desktop:

ui <- fluidPage(
  fluidRow(
    column(width = 12, offset = 0,
           class = "col-md-4",     # full-width by default, 1/3-width from "medium" screens up
           wellPanel("Resizes based on screen width"))
  )
)

Because column() ultimately just emits Bootstrap's col-* classes, any Bootstrap breakpoint class (col-sm-*, col-md-*, col-lg-*) can be added directly via class = "..." for finer control than the width argument alone provides.

Worked example: a "Next" button that advances tabs

ui <- fluidPage(
  tabsetPanel(
    id = "wizard",
    tabPanel("Step 1", p("Enter demographics"), actionButton("next1", "Next")),
    tabPanel("Step 2", p("Enter adverse events"), actionButton("next2", "Next")),

)

server <- function(input, output, session) {
  observeEvent(input$next1, updateTabsetPanel(session, "wizard", selected = "Step 2"))
  observeEvent(input$next2, updateTabsetPanel(session, "wizard", selected = "Step 3"))
}

This is the standard pattern behind any multi-step "wizard" form — each tab's own button reads as a self-contained instruction ("go to Step 2"), with all the actual navigation state living in one id.

conditionalPanel() — instant, client-side visibility

conditionalPanel() shows or hides UI based on a JavaScript expression evaluated in the browser — it reacts instantly, with no round trip to the server.

ui <- fluidPage(
  checkboxInput("advanced", "Show advanced options", value = FALSE),
  conditionalPanel(
    condition = "input.advanced == true",     # note: JS syntax, not R
    sliderInput("threshold", "Threshold", 0, 1, 0.5)
  )
)
⚠ The condition is JavaScript, not R

Inside condition = "..." you're writing a JS boolean expression against input.xyz (dot notation, JS truthiness) — not R's input$xyz. This is the one place in a typical Shiny app where you must think in JS syntax.

Conditions on multiple inputs

JS's usual boolean operators (&&, ||, !) work exactly as expected inside condition, letting you gate UI on more than one input at once:

ui <- fluidPage(
  selectInput("arm", "Arm", choices = c("Placebo", "Active")),
  checkboxInput("showSevere", "Show severe AEs only", FALSE),
  conditionalPanel(
    condition = "input.arm == 'Active' && input.showSevere == true",
    tags$p(style = "color:#C4432F;", "⚠ Reviewing severe AEs in the active arm")
  )
)
Module 14

Dynamic UI: insertUI, removeUI & renderUI

Three ways to change the actual structure of the page after it has loaded — not just show/hide, but add and remove elements entirely.

renderUI() — server-generated UI

ui <- fluidPage(
  selectInput("category", "Category", choices = c("Fruit", "Vegetable")),
  uiOutput("itemPicker")
)

server <- function(input, output, session) {
  output$itemPicker <- renderUI({
    choices <- if (input$category == "Fruit") {
      c("Apple", "Banana", "Mango")
    } else {
      c("Carrot", "Spinach", "Potato")
    }
    selectInput("item", "Item", choices = choices)
  })
}

insertUI() & removeUI() — surgical DOM edits

Unlike renderUI(), which replaces an entire placeholder's contents each time it fires, insertUI()/removeUI() add or remove elements without touching anything else already on the page — useful for "Add another row" style forms.

ui <- fluidPage(
  actionButton("addRow", "Add filter row"),
  div(id = "filterRows")
)

server <- function(input, output, session) {
  observeEvent(input$addRow, {
    insertUI(
      selector = "#filterRows",
      where = "beforeEnd",
      ui = textInput(paste0("filter", input$addRow), "New filter")
    )
  })
}

Pairing insertUI() with removeUI()

removeUI() deletes elements matching a CSS selector — commonly used to let each inserted row remove itself:

server <- function(input, output, session) {
  observeEvent(input$addRow, {
    id <- paste0("row", input$addRow)
    insertUI("#filterRows", "beforeEnd",
      div(id = id,
        textInput(paste0("filter", input$addRow), "Filter"),

}

Module 22

The reactive graph

This is the idea that makes Shiny Shiny. Everything else in the framework is scaffolding around one concept: a dependency graph that knows exactly what to recompute, and when.

Three kinds of reactive building blocks

TypeProduces a value?Runs automatically?Typical use
reactive({...})Yes — call it like a functionOnly when read, and only if staleShared, cached computation used by multiple outputs
observe({...}) / observeEvent()No — used for side effectsYes, whenever a dependency changesNotifications, updating inputs, writing to a database
render*({...})Yes — implicitly, to an output$Yes, whenever a dependency changesProducing the actual content of an output

The rule underneath all of it: a reactive expression automatically knows what it depends on, simply by which reactive values it reads while it runs. There's no manual subscription list — Shiny tracks it every time the block executes.

Fig. 2 — one reactive expression shared by two outputs. It runs once per change, not once per consumer.

Invalidation, not re-execution, is the first step

When input$bins changes, Shiny doesn't immediately re-run anything. It first walks the graph marking every downstream node invalidated (stale). Only during the next flush — a single batched pass — does it actually re-execute invalidated nodes, in dependency order, each exactly once. This two-phase design is why changing five inputs in the same tick of the event loop doesn't trigger five separate redraws of a shared output — only one.

Module 23

reactive() — reactive expressions

Use reactive() whenever more than one output needs the same intermediate result.

server <- function(input, output, session) {

  filteredData <- reactive({
    subset(mtcars, mpg >= input$minMpg)
  })

  output$plot <- renderPlot({
    plot(filteredData()$wt, filteredData()$mpg)
  })

  output$table <- renderTable({
    filteredData()
  })
}

filteredData is not a data frame — it's a function. Calling filteredData() either returns a cached value (nothing it depends on has changed) or re-runs the block once and caches the new result. Both outputs above share that single computation, instead of each re-filtering mtcars independently.

Laziness: reactive() only runs when read

A reactive() block that nothing ever reads never executes — even if its own dependencies change. This is different from observe() (Module 24), which runs proactively. Laziness is what makes reactive() safe to define speculatively without worrying about wasted computation.

server <- function(input, output, session) {
  expensive <- reactive({
    message("Computing...")   # only prints if expensive() is actually called somewhere
    Sys.sleep(1)
    input$x * 2
  })
  # If no output ever calls expensive(), "Computing..." never prints.
}

Caching across users with bindCache()

For expensive computations that produce the same result for the same inputs across different users, bindCache() lets Shiny skip recomputation entirely and reuse a stored result:

filteredData <- reactive({
  expensive_join(input$region, input$year)
}) |> bindCache(input$region, input$year)

Chaining reactives into a pipeline

Reactive expressions can depend on other reactive expressions, not just on input$ — this is how you build a readable, multi-stage pipeline instead of one dense block:

server <- function(input, output, session) {

  rawSubset <- reactive({
    subset(ae_data, arm %in% input$arm)
  })

  severityFiltered <- reactive({
    subset(rawSubset(), severity_rank >= input$minSeverity)
  })

  summaryCounts <- reactive({
    aggregate(patient_id ~ ae_term, data = severityFiltered(), FUN = length)
  })

  output$table <- renderTable({ summaryCounts() })
}

Changing input$arm invalidates all three stages; changing input$minSeverity only invalidates the last two — rawSubset() stays cached. Each stage is independently readable, testable, and reusable by other outputs.

Module 24

observe() & observeEvent()

Reactive expressions produce values. Observers produce side effects — and never return anything meaningful.

server <- function(input, output, session) {

  # Fires whenever ANY reactive value it reads changes.
  observe({
    message("input$x is now: ", input$x)
  })

  # Fires ONLY when input$submit changes (i.e. is clicked) —
  # ignores changes to any other input read inside the block.
  observeEvent(input$submit, {
    showNotification("Form submitted!", type = "message")
  })
}

observe() vs. observeEvent(): when to use which

observe({})observeEvent(trigger, {})
DependenciesEverything read inside the blockOnly the explicit trigger expression
Best forLogging/syncing that should track several inputs at onceActions gated behind one specific event, like a button
RiskEasy to accidentally depend on more than intendedLow — dependencies are explicit and visible
💡 Default advice

Reach for observeEvent() first. It reads like a sentence — "when this happens, do that" — and its dependency is explicit, which avoids a whole class of accidental-retrigger bugs.

Useful observeEvent() parameters

observeEvent(input$submit, {
  log_submission(input$form)
},
  ignoreInit = TRUE,   # don't fire once automatically when the app first loads
  once = TRUE          # fire at most one time ever, then stop listening
)

# Trigger on EITHER of two inputs changing
observeEvent(list(input$arm, input$severity), {
  message("A filter changed")
})

ignoreInit = TRUE matters more than it looks: by default, observeEvent()/eventReactive() fire once immediately at startup, even before the user has touched anything — usually harmless, but surprising the first time you see a notification pop up on page load.

Module 26

isolate() — reading without depending

Lets a reactive block read a value without creating a dependency on it.

observeEvent(input$go, {
  # This block only re-runs when input$go changes.
  # input$label is read but NOT tracked, thanks to isolate().
  message("Running with label: ", isolate(input$label))
})

eventReactive() and observeEvent() are, in fact, implemented internally using isolate() under the hood — they isolate everything in the block except the explicit trigger expression. Understanding isolate() is what lets you build the same pattern by hand when the built-ins aren't flexible enough — for example, isolating just one of several reads inside an observe().

⚠ A common trap: reading input$x outside a reactive context

Reactive values (like input$x) can only be read inside a reactive context — a reactive(), observe(), render*(), or similar. Reading one directly at the top level of your server function throws Operation not allowed without an active reactive context. isolate() is one way to read a value from outside such a context, e.g. once at session start.

Worked example: snapshotting state without tracking it

server <- function(input, output, session) {

  auditLog <- reactiveVal(list())

  observeEvent(input$approve, {
    # We want to RECORD input$reviewer and input$comment at the moment of
    # approval, but neither should be able to trigger this block on its own —
    # only input$approve should. isolate() achieves exactly that.
    entry <- list(
      time = Sys.time(),
      reviewer = isolate(input$reviewer),
      comment  = isolate(input$comment)
    )
    auditLog(c(auditLog(), list(entry)))
  })
}

Without isolate() here, this observeEvent() would still only fire on input$approve (that's what observeEvent()'s trigger argument already guarantees) — but wrapping the reads in isolate() makes that guarantee visible in the code itself, which matters once a block gets long enough that its real dependency isn't obvious at a glance.

A reset button, and why it needs isolate()

server <- function(input, output, session) {
  history <- reactiveVal(numeric(0))

  observeEvent(input$record, {
    history(c(isolate(history()), input$value))
  })

  observeEvent(input$reset, {
    history(numeric(0))
  })
}

Notice isolate(history()) is written explicitly even though it's technically redundant here — observeEvent() already isolates everything in its handler except the trigger expression itself (Module 24). Writing it anyway documents intent for the reader. If you instead used a plain observe({ history(c(history(), input$value)) }), that explicit isolate() would stop being optional: without it, reading history() inside a block that also writes it creates a self-dependency and an infinite loop.

Module 28

input / output / session — deep dive

The three arguments every server function receives, and what each one is actually for.

input — read-only, list-like, reactive

input behaves like a named list, but every field is a reactive value — reading input$x inside a reactive context creates a dependency. You cannot assign to it directly (input$x <- 5 throws an error) — that's what update*Input() functions are for (Module 29).

output — write-only

output is where you assign the results of render*() calls. You should never try to read from output$x — it's a one-way channel from server logic to the browser.

session — the escape hatch

server <- function(input, output, session) {

  # Run cleanup code when a session ends (tab closed, connection dropped)
  session$onSessionEnded(function() {
    message("A user's session just ended.")
  })

  # Read the URL query string, e.g. ?user=42
  observe({
    query <- parseQueryString(session$clientData$url_search)
    print(query$user)
  })

  # Client-side info: browser window size, pixel ratio, URL, etc.
  output$dims <- renderText({
    paste(session$clientData$output_plot_width, "×", session$clientData$output_plot_height)
  })
}

⚠ Avoid update-loops

An observeEvent(input$x, updateXInput(session, "x", ...)) that sets x to a genuinely new value will re-trigger itself. Shiny deduplicates identical consecutive values to prevent infinite loops, but logic that always produces a different value each time can still spin — guard with a condition if needed.

Worked example: a three-level cascading filter

ui <- fluidPage(
  selectInput("study", "Study", choices = c("Study 001", "Study 002")),
  selectInput("arm", "Arm", choices = NULL),
  selectInput("subject", "Subject", choices = NULL)
)

server <- function(input, output, session) {

  observeEvent(input$study, {
    arms <- arms_for_study(input$study)
    updateSelectInput(session, "arm", choices = arms)
  })

  observeEvent(input$arm, {
    req(input$arm)
    subjects <- subjects_for_arm(input$study, input$arm)
    updateSelectInput(session, "subject", choices = subjects)
  }, ignoreInit = TRUE)
}

Each level only knows about the level directly above it — study drives arm, arm drives subject — and updating one automatically cascades because changing arm's choices fires its own observeEvent() in turn. ignoreInit = TRUE on the second observer avoids populating subject before arm has ever actually changed.

Validation — req(), validate(), need()

Two different failure modes for reactive code: quietly waiting, and visibly explaining.

req() — gracefully waiting for input

req() silently stops execution of the current reactive block if its argument isn't yet available (e.g. an empty text box, or a file not yet uploaded) — instead of throwing a visible error.

output$plot <- renderPlot({

Module 32

Shiny modules

A Shiny module is a mini app-within-an-app: a UI function and a server function, paired together, whose input/output IDs are automatically namespaced so they can't collide with the rest of your app.

Once an app grows past a few hundred lines, or you find yourself copy-pasting a control into several tabs, it's time to extract a module. Modules are ordinary R functions — they compose, take arguments, and can be tested independently of the rest of the app.

Anatomy of a module

library(shiny)

# --- UI function -----------------------------------------------------
histogramUI <- function(id) {
  ns <- NS(id)                       # namespace helper, tied to this id
  tagList(
    sliderInput(ns("bins"), "Bins", min = 5, max = 50, value = 20),
    plotOutput(ns("plot"))
  )
}

# --- Server function ---------------------------------------------------
histogramServer <- function(id, data) {
  moduleServer(id, function(input, output, session) {
    output$plot <- renderPlot({
      hist(data(), breaks = input$bins, col = "steelblue", border = "white")
    })
  })
}

Every inputId/outputId inside the module is wrapped in ns(...), which prefixes it with the module's instance ID (e.g. "panel1-bins"). That means the same module can be mounted twice in one app, and the two copies never interfere with each other.

library(shiny)
source("modules/histogram_module.R")

ui <- fluidPage(

  fluidRow(
    column(6, h4("Old Faithful — waiting"), histogramUI("panel1")),
    column(6, h4("mtcars — mpg"),          histogramUI("panel2"))
  )
)

server <- function(input, output, session) {
  histogramServer("panel1", data = reactive(faithful$waiting))
  histogramServer("panel2", data = reactive(mtcars$mpg))
}

shinyApp(ui, server)

Communication between modules

Modules communicate through ordinary R function arguments and return values — a module can accept a reactive() as an argument (as above with data), and can return() a reactive expression for its caller to use elsewhere.

filterUI <- function(id) {
  ns <- NS(id)
  selectInput(ns("cyl"), "Cylinders", choices = sort(unique(mtcars$cyl)), multiple = TRUE)
}

filterServer <- function(id) {
  moduleServer(id, function(input, output, session) {
    # Return a reactive so the PARENT app can react to this module's state
    reactive({
      req(input$cyl)
      subset(mtcars, cyl %in% input$cyl)
    })
  })
}
server <- function(input, output, session) {
  filtered <- filterServer("filters")     # returned reactive from the module

  output$plot <- renderPlot({
    plot(filtered()$wt, filtered()$mpg)   # used directly in the parent app
  })
}
💡 When to reach for modules

As soon as a piece of UI + logic is used more than once, or a single-file app becomes hard to navigate — usually somewhere past 200–300 lines. Split by feature ("filters", "upload"), not by file type.

Creating a variable number of module instances

Modules aren't limited to a fixed number of copies written by hand — lapply() can mount one per element of a vector, which is how you'd build "one card per study site" or "one panel per treatment arm" without knowing the count in advance:

arms <- c("Placebo", "Low Dose", "High Dose")

ui <- fluidPage(
  fluidRow(
    lapply(arms, function(a) {
      column(4, summaryCardUI(id = a))    # one module instance per arm, id = arm name
    })
  )
)

server <- function(input, output, session) {
  lapply(arms, function(a) {
    summaryCardServer(id = a, data = reactive(subset(trial_data, arm == a)))
  })
}
⚠ Force evaluation inside the loop

In older R/Shiny code you may see local({ a <- a; ... }) wrapped around the loop body — a workaround for lazy evaluation capturing the wrong a. Modern lapply()-based module instantiation like above does not need this, since each call gets its own function-call environment.

server <- function(input, output, session) {

  severityRank <- c(Mild = 1, Moderate = 2, Severe = 3)

  filtered <- reactive({
    req(input$arm)
    subset(trial_data,
           arm %in% input$arm &
           severityRank[severity] >= severityRank[input$severity])
  })

  output$nEnrolled <- renderText({ nrow(filtered()) })

  output$nWithAE <- renderText({
    sum(filtered()$ae_term != "None")
  })

  output$nSevere <- renderText({
    sum(filtered()$severity == "Severe")
  })

  output$aeTable <- renderDT({
    datatable(
      subset(filtered(), ae_term != "None",
             select = c(patient_id, arm, age, sex, ae_term, severity)),
      options = list(pageLength = 8), rownames = FALSE
    )

    validate(need(nrow(filtered()) > 0, "No subjects match the current filters"))
    ggplot(subset(filtered(), ae_term != "None"), aes(x = arm, fill = severity)) +
      geom_bar(position = "stack") +

    ggplot(ordered, aes(enrollment_date, cumulative)) +
      geom_step(color = "#3B54D6", linewidth = 1) +
      labs(x = NULL, y = "Cumulative subjects enrolled") +
      theme_minimal()

    filename = function() paste0("ae_listing_", Sys.Date(), ".csv"),

  )
}

What happens, step by step

  1. The committee unchecks Placebo in the sidebar. That's a change to input$arm.
  2. Shiny invalidates filtered() (Module 22) — it's the only reactive expression that reads input$arm.
  3. Because nEnrolled, nWithAE, nSevere, aeTable, aeByArm, and enrollCurve all call filtered(), all six are invalidated too — but filtered() itself only re-executes once (Module 23's laziness-plus-caching), not six times.
  4. Each output then re-renders independently from that single shared, filtered subset — the AE bar chart, the enrollment curve, and the listing table all stay perfectly in sync with no extra code required to keep them consistent.
  5. Clicking Download AE listing hands the current filtered() result — exactly what's on screen — to downloadHandler() (Module 37), so the exported CSV always matches the visible filters.

Key learning points

  • One reactive, many consumers. This is the pattern from Module 23 doing real work — six outputs, one source of truth, zero duplicated filtering logic.
  • validate()/need() for the "empty result" case (Module 30) — unchecking every arm shouldn't crash the chart, it should explain itself.
  • Named-vector lookups double as data recoding — severityRank[severity] turns an ordered factor-like column into a comparable integer in one line, a common clinical-data idiom.
  • The download always matches the screen because both read the same filtered() reactive — a subtle but important correctness guarantee for anything a committee might sign off on.

Summary

Nothing in this dashboard is a new Shiny concept — it's Modules 17 (choices), 22–23 (the reactive graph and reactive()), 30 (validation), 34 (bslib layout), 35 (DT), 36 (ggplot2 plots), and 37 (downloads), composed around a domain a clinical audience recognizes immediately. That composability — small, well-understood pieces combining into a real tool — is the actual skill this guide is teaching.

Module 38

Asynchronous programming & debugging

By default, a Shiny process handles one thing at a time per session — a slow computation for one user blocks that user's whole app until it finishes. Async patterns fix this; debugging tools help you see the reactive graph clearly.

promises & future — non-blocking long tasks

library(shiny)
library(promises)
library(future)
plan(multisession)   # run futures in background R processes

server <- function(input, output, session) {
  output$result <- renderText({
    future({
      Sys.sleep(3)          # simulate a slow computation
      "Done!"
    }) %...>% { . }         # resolve the promise into the render output
  })
}
Async helps other sessions, not this one

future() frees the current session from blocking on this one computation, and — critically — frees the R process to keep serving other users' sessions while it waits. It does not make the computation itself faster.

browser() — breakpoints inside reactive code

output$plot <- renderPlot({
  browser()                 # execution pauses here when this block runs
  plot(filteredData())
})

When a reactive block hits browser(), execution pauses in the R console with full access to that block's local variables — including the current value of any input$ or reactive() it has already read.

Visualizing the reactive graph with reactlog

Catching errors gracefully in production

An uncaught error inside a reactive block normally shows the user a generic "An error occurred" message and stops that output — options(shiny.sanitize.errors = ...) and per-block tryCatch() control how much detail leaks through:

options(shiny.sanitize.errors = TRUE)   # hide internal error text from end users in production

output$result <- renderTable({
  tryCatch({
    risky_computation(input$x)
  }, error = function(e) {
    validate("Something went wrong processing that input — please check the values and try again.")
  })
})
⚠ Sanitized errors still log server-side

shiny.sanitize.errors only affects what the browser sees — the real error and stack trace still print to the R console/server logs, which is where you should be looking when debugging a production issue.

Module 39

Performance optimization

Most Shiny performance problems trace back to one of a small set of causes — this module is a checklist.

  • Share, don't repeat. If two outputs compute the same filtered/joined data, wrap it once in reactive() (Module 23) instead of recomputing it in each render*().
  • Debounce noisy inputs. A text box that fires on every keystroke can flood the server — wrap it with debounce() to wait for the user to pause typing.
  • Isolate what shouldn't retrigger. Use isolate() (Module 26) or eventReactive() (Module 25) to stop a block from re-running on inputs it only needs to read once per action.
  • Cache across sessions. bindCache() (Module 23) skips recomputation entirely for repeated inputs.
  • Go async for slow, independent work. future()/promises (Module 38) frees the process to serve other users while one computation runs.
  • Profile before optimizing. Use profvis::profvis(runApp()) to see exactly where time is spent before changing anything.
server <- function(input, output, session) {
  searchTerm <- reactive({ input$search }) |> debounce(400)

  output$results <- renderTable({
    req(searchTerm())
    search_database(searchTerm())
  })
}
install.packages("profvis")
profvis::profvis(shiny::runApp("app.R"))

Memoizing plain R functions with memoise

bindCache() (Module 23) caches a reactive expression's result; memoise does the same for an ordinary R function, useful for helper functions called from several places, including outside any reactive context:

library(memoise)

slow_lookup <- function(subject_id) {
  Sys.sleep(2)          # simulate a slow database/API call
  query_registry(subject_id)
}

fast_lookup <- memoise(slow_lookup)   # identical calls after the first return instantly

server <- function(input, output, session) {
  output$info <- renderPrint({
    fast_lookup(input$subjectId)
  })
}

Testing Shiny apps

Reactive apps can be tested at two levels: server logic in isolation, and full end-to-end browser behavior.

testServer() — testing reactive logic directly

library(shiny)
library(testthat)

test_that("counter increments correctly", {
  testServer(server, {
    session$setInputs(bump = 1)
    expect_equal(input$bump, 1)

    session$setInputs(bump = 2)
    expect_equal(output$count, "Clicked 2 times")
  })
})

shinytest2 — full end-to-end tests

library(shinytest2)

test_that("app loads and slider updates the plot", {
  app <- AppDriver$new(app_dir = ".")
  app$set_inputs(bins = 35)
  app$expect_screenshot()
  app$stop()
})

shinytest2 drives a real, headless browser against a real, running instance of your app — it can click buttons, fill in text, and compare screenshots across runs to catch visual regressions, not just logic bugs.

Worked example: testing a filter's output value

test_that("selecting only the Active arm filters out Placebo rows", {
  testServer(server, {
    session$setInputs(arm = "Active", severity = "Mild")
    result <- filtered()
    expect_true(all(result$arm == "Active"))
    expect_false(any(result$arm == "Placebo"))
  })
})

Testing the reactive expression itself (filtered()) rather than only the rendered output is usually the higher-value test — it verifies the actual filtering logic independent of how any particular output happens to display it.

Security considerations

  • Never trust input$ values. They come directly from the browser and can be manipulated — validate before using them in file paths, SQL, or shell commands.
  • Avoid building SQL with paste/glue on raw input — use parameterized queries (DBI::dbGetQuery(con, "SELECT * FROM t WHERE id = ?", params = list(input$id))).
  • Restrict file access. fileInput() uploads go to a Shiny-managed temp path — don't let user input control which server-side file paths get read or written.
  • Set an upload size limit (Module 18) to avoid denial-of-service via huge uploads.
  • Serve over HTTPS in production — Posit Connect and shinyapps.io handle this for you; self-hosted Shiny Server needs a reverse proxy (nginx/Apache) in front of it.

Managing credentials with .Renviron

Never hardcode database passwords or API tokens in app.R — read them from environment variables instead, set locally in a .Renviron file (excluded from version control) and configured as secrets in your deployment target:

DB_HOST=clinical-db.internal
DB_USER=shiny_reader
DB_PASSWORD=************
con <- DBI::dbConnect(
  RPostgres::Postgres(),
  host = Sys.getenv("DB_HOST"),
  user = Sys.getenv("DB_USER"),
  password = Sys.getenv("DB_PASSWORD")
)
⚠ Add .Renviron to .gitignore

A .Renviron file containing real credentials should never be committed. Posit Connect and shinyapps.io both provide their own secret/environment-variable configuration in their deployment settings — set values there for the deployed app, and keep a local-only .Renviron for development.

summaryCardServer <- function(id, data, title) {
  moduleServer(id, function(input, output, session) {
    output$title <- renderText(title)
    output$plot <- renderPlot({
      ggplot(data(), aes(mpg)) +
        geom_histogram(bins = 15, fill = "#3B54D6", color = "white") +
        theme_minimal()
    })
  })
}

# ---- UI -------------------------------------------------------------------
ui <- page_sidebar(
  title = "Mini Motor Trends Explorer",
  theme = bs_theme(version = 5, primary = "#3B54D6"),

  sidebar = sidebar(
    selectInput("cyl", "Cylinders", choices = sort(unique(mtcars$cyl)),
                selected = sort(unique(mtcars$cyl)), multiple = TRUE),
    sliderInput("mpgRange", "MPG range", min = floor(min(mtcars$mpg)),
                max = ceiling(max(mtcars$mpg)),
                value = c(floor(min(mtcars$mpg)), ceiling(max(mtcars$mpg)))),
    downloadButton("dl", "Download filtered CSV")
  ),

  layout_columns(
    col_widths = c(6, 6, 12),
    summaryCardUI("card1"),
    card(card_header("Weight vs. MPG"), plotOutput("scatter", height = 220)),
    card(card_header("Filtered data"), DTOutput("table"))
  )
)

# ---- server -----------------------------------------------------------------
server <- function(input, output, session) {

  filtered <- reactive({
    req(input$cyl)
    subset(mtcars,
           cyl %in% input$cyl &
           mpg >= input$mpgRange[1] &
           mpg <= input$mpgRange[2])
  })

  summaryCardServer("card1", data = filtered, title = "MPG distribution")

  output$scatter <- renderPlot({
    validate(need(nrow(filtered()) > 0, "No cars match this filter"))
    ggplot(filtered(), aes(wt, mpg, color = factor(cyl))) +
      geom_point(size = 3) +
      labs(color = "Cyl") +
      theme_minimal()
  })

  output$table <- renderDT({
    datatable(filtered(), options = list(pageLength = 5))
  })

  output$dl <- downloadHandler(
    filename = function() "filtered_mtcars.csv",
    content  = function(file) write.csv(filtered(), file, row.names = TRUE)
  )
}
